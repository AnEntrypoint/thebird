# Canonical web host, txiki.js runtime and fx-programmed features

A thebird web host is the canonical local serving path for the built site. It serves `_site/` as a normal browser URL on `127.0.0.1:4173`, with the cross-origin isolation headers required by the browser WASM runtime. The page runs **txiki.js in the browser** (`web/vendor/txiki/tjs.wasm` through `web/txiki-in-page.js`); Node only sends static files. The older `bin/thebird-relay.js` remains as a source-tree terminal server for development, but it is not the canonical site-host path.

## Quick start

```bash
node scripts/build-pages.mjs
npm run host
```

Open `http://127.0.0.1:4173/`. The generated `index.html` loads the terminal bundle, which imports `web/features.js`, `web/features-bridge.js` and `web/features-in-txiki.js`. `web/features.json` registers a small fx-programmed demo card. Add `?featureProgram=1` to also run `web/features-program.js` inside txiki and register a second visible card through the in-page bridge:

```text
http://127.0.0.1:4173/?featureProgram=1
```

The host prints its URL, root, isolation mode, PID and log path. It sends:

```text
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

These headers let SharedArrayBuffer, OPFS/worker paths, Ctrl-C cancellation and the txiki.js WASM cancel path work in a normal browser tab. `--no-isolation` is a compatibility-only fallback for plain static asset inspection; do not use it for the terminal runtime.

## Commands

| Command | Purpose |
| --- | --- |
| `npm run host` | Canonical: start the managed isolated host for `_site/` and print `http://127.0.0.1:4173/`. |
| `npm run host:status` | Print `running <url> pid <pid> root <root>`, or exit 1 with `stopped`. |
| `npm run host:check` | Check the pinned txiki wasm, HTTP status/content types/COOP+COEP, and headless Chromium DOM including fx/txiki visible features. |
| `npm run host:stop` | Stop only the host recorded for the same host, port and root. |
| `npm run host:serve` | Run the same isolated host in the foreground. |
| `npm start` | Legacy source-tree terminal relay; useful for direct `web/` development but not the canonical built-site host. |

All `bin/thebird-web-host.js` actions accept `--host`, `--port`, `--root` and, for compatibility, `--no-isolation`:

```bash
node bin/thebird-web-host.js start --host 127.0.0.1 --port 4173 --root _site
node bin/thebird-web-host.js status --host 127.0.0.1 --port 4173 --root _site
node bin/thebird-web-host.js stop --host 127.0.0.1 --port 4173 --root _site
```

## txiki.js and vendor status

The canonical host serves `web/vendor/txiki/tjs.wasm` from `_site/`. The generated wasm is gitignored; `node scripts/vendor-txiki.mjs` builds it with Zig 0.17.1 and `scripts/txiki/` browser bindings. `scripts/txiki/pin.json` records the required SHA-256, and `npm run host:check` verifies the served wasm against that pin before checking the browser. If the wasm is absent, run `node scripts/vendor-txiki.mjs`, then `node scripts/build-pages.mjs`. `web/vendor/fx/` is committed, generated by `scripts/vendor-fx.mjs`; the `fx` builtin reads its manifest and core WASM from the site.

`web/txiki-in-page.js` exposes `runTjs` and `tjsBuiltin`. Builtins including `tjs`, `qjs`, `node`, `npm`, `curl`, `sqlite3`, `git`, `fx`, `playwriter` and `feature` are registered in `web/builtins.js` and run through the txiki VM or its in-page bridge.

## Visible feature API

`web/features.js` mounts `<aside id="features">` and defines `window.THEBIRD_FEATURES` (also `globalThis.thebird.features`):

```js
const id = window.THEBIRD_FEATURES.register('my-card', {
  title: 'My fx feature',
  description: 'Visible DOM content',
  status: 'ready',
  body: [
    { type: 'p', text: 'Hello from fx' },
    { type: 'button', id: 'hello', label: 'Press me' },
    { type: 'canvas', width: 180, height: 48, text: 'fx canvas' }
  ]
}, { source: 'fx' });

window.THEBIRD_FEATURES.update(id, { status: 'updated' });
window.THEBIRD_FEATURES.remove(id);
window.THEBIRD_FEATURES.list();
window.THEBIRD_FEATURES.clear();
```

Cards support plain text, arrays, safe HTML element specs, buttons and canvas elements. Register, update, remove, list and clear are idempotent; ids must match `[A-Za-z][A-Za-z0-9_-]*`. The registry emits `feature:registered`, `feature:updated`, `feature:removed` and button events through `THEBIRD_FEATURES.on` and matching DOM `CustomEvent`s.

`web/features.json` is a fetchable declarative request document. `web/features-bridge.js` exposes `applyFeatureRequest(payload)`, `loadFeatureRequests(url)` and `globalThis.THEBIRD_FEATURE_BRIDGE`. On page boot, the bridge fetches `features.json` and registers its requests; this is the small fx demo visible in headless Chromium DOM checks.

### txiki.js programs

A txiki program can register visible features through the existing `__thebirdBridge` builtin channel. `web/features-program.js` is a working example: it sends `{ op: 'register', id, spec, source }` messages to the `feature` builtin and fetches `features.json` with the browser `fetch` provided by txiki's browser bindings. `web/features-in-txiki.js` loads that program into `runTjs` and exposes `window.thebird.runFeatureProgram()`. The URL parameter `?featureProgram=1` calls it during page boot, so a normal browser DOM check can prove that code inside txiki produced visible DOM.

Program-side message shape:

```js
__thebirdBridge.send(JSON.stringify({
  op: 'builtin',
  id: 1,
  name: 'feature',
  argv: [JSON.stringify({ op: 'register', id: 'txiki-card', source: 'txiki', spec: { title: 'From txiki' } })],
  cwd: '/workspace'
}));
```

The `feature` builtin in `web/builtins.js` applies the same `applyFeatureRequest` function as page/fx code. No online infrastructure is used: all modules and manifests are same-origin static files served by the canonical host.

## Safe lifecycle

`start` writes one state file under gitignored `.thebird/web-host/`, keyed by host, port and resolved root. `status` and `stop` read that state, confirm the PID is alive, and read `/proc/<pid>/environ` for the matching `THEBIRD_WEB_HOST_TAG`. They never signal an unrelated process and never use a name pattern, `pkill` or `killall`. `stop` sends `SIGTERM` to the recorded child only. The foreground runner closes on `SIGINT` and `SIGTERM`.

## Verification

```bash
npm run check
npm run lint:comments
npm run lint:architecture -- --static
npm run host:check
```

`npm run host:check` runs `node scripts/build-pages.mjs` first, so it always starts from the real built `_site/`. It fails early if any feature module, `features.json`, the txiki wasm or the bundled feature wiring is missing; `npm run host` also refuses an isolated site root that lacks those canonical runtime files. It then verifies the txiki wasm SHA-256, starts the canonical host, checks HTTP 200 and the HTML/WASM/JSON content types, checks both isolation headers, then uses `scripts/dump-dom-ready.mjs` to launch headless Chromium and wait through DevTools for `data-boot="ready"`, `data-engine="ready"` and the txiki feature markers before returning the settled DOM. It asserts `<title>thebird</title>`, `data-engine="ready"`, `data-feature-program="ready"`, `data-feature-count="2"`, the `fx-visible-demo` card and the `txiki-visible-demo` card. The checker stops its own host in a `finally` block and the helper stops only the Chromium PID it starts. Set `CHROME_BIN` for a non-default Chromium.

## Hosted webserver system

The canonical host is also the live parent for registered Node webservers. See `docs/WEBSERVER_STANDARD.md` for the standard contract, normal commands, SDK, MCP/fx hookups, responsive shell, HMR/SSE and user-wide prompts. `npm run host:check` registers and unregisters a temporary test server against the live registry while preserving the canonical 27-check baseline.
