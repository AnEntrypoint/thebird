# thebird

Browser-native web OS — agentic chat, POSIX terminal, live preview, IndexedDB filesystem.

Repo: https://github.com/AnEntrypoint/thebird.git
Local dev (web-OS): `bunx serve docs` (or `npx serve docs` / `python -m http.server -d docs`).
Local dev (landing): `npx flatspace build && npx serve dist`.
Live: https://anentrypoint.github.io/thebird/

Package manager: bun is canonical (`bunx` drives every documented dev/onboarding command; `bun.lock` is the tracked lockfile). No CI job runs `npm ci`/`npm install`/`bun install` against the root `package.json` — `npx`/`bunx` here are one-shot tool runners, not lockfile-based installs — so `package-lock.json` was vestigial (deleted) and `docs/` needs no build step.

Commit convention: Conventional Commits (`feat(scope):`, `fix(scope):`, `chore(scope):`) is the de-facto history convention — keep it.

Docs map (Diataxis): tutorial = "Just-works onboarding" below (full walkthrough + tool list + limitations: `docs/SETUP.md`); how-to = `docs/MANUAL-VALIDATION.md`; reference = this file; explanation = `ARCHITECTURE.md`.

## Just-works onboarding
1. `bunx acptoapi@latest` (binds :4800, autolaunches ACP daemons, exposes `/v1/chat/completions`).
2. `bunx serve docs` -> open in browser -> chat. Defaults route to `auto` over localhost:4800; gm wasm loads in-page; tools (read/write/edit/grep/list/memory/chat/delegate/web_search/gm) registered automatically.
3. acptoapi 1.0.116+ adds response cache (`X-Acptoapi-Cache: hit|miss|dedupe|bypass`, `/v1/cache/stats`) and opt-in idle pretest (`ACPTOAPI_PRETEST_ENABLED=1`).

The full web-OS lives in `docs/` (no install, no build — static server). GH Pages landing is a flatspace build under `site/` deployed via `.github/workflows/gh-pages.yml`.

## Validation policy: exhaustive manual troubleshooting/debugging only

This project keeps **no automated test suites** — no unit/spec files, no `test/`/`__tests__/` directories, no test frameworks, and no CI workflows whose job is running tests (the old `validate.html` harness and the `witness-ci.yml`/`witness-core.yml` workflows were all removed; they flaked and diverged from local reality). Validation is done **exclusively by exhaustive manual troubleshooting and debugging**: boot the real OS (`bunx serve docs`, + `bunx acptoapi@latest` for chat) and drive it by hand — live browser inspection, and the `scripts/witness-*.mjs` puppeteer probes run manually as debugging tools (see `docs/MANUAL-VALIDATION.md`). A change is validated when its real code path has been run and its real output observed, never when a suite goes green. The only CI checks kept are non-test guards: `gh-pages.yml` (deploy), `syntax-check.yml` (parse lint), `sw-drift.yml` (codegen-drift guard), `sync-upstream.yml` (vendor freshness).

## Making a game with zero code (level editor)

thebird ships one authoring tool today: the **level editor** app (`docs/examples/apps/level-editor-app.js`, registered as `level-editor` in `apps.js`). It is deliberately small — a canvas you place objects on, a live property inspector, and a save/export flow — not a full game engine. What it gives a non-coder right now:

1. Open the **level editor** app from the desktop.
2. Click `+ block` / `+ actor` / `+ goal` to place an object on the canvas.
3. Drag objects to reposition them; click one to select it.
4. Edit its `name`, `x`, `y`, `width`, `height`, `color`, `label` live in the right-hand inspector — changes reflect on the canvas immediately.
5. Click `save` to persist the scene (versioned JSON, per-instance fs) or `export .json` to download a portable copy.
6. Open the **game-player** app (`docs/examples/apps/game-player-app.js`, registered as `game-player`) and pick the saved scene — it RUNS it via the level editor's exported `runScenePlaytest()` runner, no further code needed.

Under the hood: the play-test loop is an ECS-driven simulation (`runScenePlaytest()` builds a docs/lib/ecs.js world: objects as entities, an inputMovementSystem for arrow-key actors, and a chainSystem that executes the scene's optional `chains` event graphs via `docs/lib/event-chain-runtime.js`, the executor for the `docs/lib/event-chain.js` trigger→condition→action model), and chains are authored in the editor's collapsible **event chains** panel — deliberately list-based, not a node-graph canvas: `+ chain` / `+ node`, a `type:kind` select per node, kind-appropriate config fields (object pickers = dropdowns of scene objects), and `then ->` / `if true ->` / `if false ->` edge dropdowns with detectCycles-backed cycle rejection. What it is **not** (yet): behavior beyond that scene/chain runtime — for a real hand-written app, see the next section.

## Writing your own app without touching the registry (user apps)

Beyond the level editor's zero-code path, thebird also supports **user-authored apps**: any `apps/*.js` file written into an instance's own filesystem is discovered, registered, and made launchable without editing `docs/apps.js` or restarting the OS (`docs/lib/user-apps.js`, wired into `docs/os-shell.js`).

1. From a terminal (or the notes/files app), create `apps/my-app.js` in the current instance's fs.
2. Export a factory — either `export default` or `export function createApp` — shaped `({ instance }) => ({ node, dispose?, getViewState?, restoreViewState? })`. `instance` is the same per-instance handle `docs/apps.js` factories get (`instance.fs`, `instance.id`, ...); `node` is the DOM node mounted into the window body.
3. The app appears in the apps menu/side-rail/drawer as `user-my-app` (basename-derived, no restart needed).
4. Editing the file hot-reloads any open window of it in place (view state carried via `getViewState`/`restoreViewState`); a broken module (syntax error, missing factory, throwing factory) shows a visible error pane instead of a silent dead window — fix the file and it recovers on the next debounced write.
5. Modules import through a fresh `blob:` URL per load, so they must be self-contained (no relative/bare-specifier imports — an absolute `https://` import works, e.g. from unpkg).

This is a lower-level, code-first authoring surface than the level editor (which is scene/behavior-only, zero JS); user apps are full DOM apps with the same shape `createAppRegistry`'s own `reg()` factories produce, just discovered from the instance fs instead of hardcoded at boot. See `docs/lib/user-apps.js`'s header comment for the full module/registry/lifecycle contract (blob-URL import, debounced hot-reload, per-instance registry scoping, view-state re-stamping guard against a lossy vendored kit).

### Architecture & boundaries
- **"thebird dynamic stack contract freddie acptoapi"** — layered stack rule; thebird never imports acptoapi or fetches LLM providers directly; freddie is the only LLM-facing API; configuration precedence; vendor sync via `scripts/sync-upstream.mjs`.
- **"thebird GUI boundary rule anentrypoint-design upstream"** — visual code upstream in `anentrypoint-design`, functional code in thebird; `renderWindow`/`renderDock`/`createDesktopShell`/`<freddie-chat>` API shapes; refresh via `scripts/refresh-design.mjs`.
- **Kit consumption: two paths, both tracking latest, no third copy.** The `247420.css` bundle loads live from `https://unpkg.com/anentrypoint-design@latest` on every served page; the finer-grained `kits/os` + `components` + `web-components` JS/CSS subtrees are vendored into `docs/vendor/` because they are imported as real modules and cannot come from a CDN bundle. `scripts/refresh-design.mjs` uses a local working tree when one exists and the npm `@latest` tarball otherwise (no hardcoded dev-box path), stamping `docs/vendor/kits/os/.version` with which source supplied the bytes — check that stamp before trusting the vendored kit's freshness. Fleet-wide: Node-resolved consumers (freddie, casey) take the npm dep at `latest`, never a caret (on the kit's `0.0.x` line a caret is a hard pin that floats nothing); browser-delivered consumers (thebird, zellous, spoint) load unpkg `@latest`. **gmsniff** (air-gapped, zero external-origin fetches, must never be a supply-chain surface for the agent host it observes) and **agentgui** (offline, deliberately non-shifting UI) are permanent, deliberate exclusions — not drift to reconcile.

This does NOT change what ships: `--npm` (what CI always passes) still forces the published npm/unpkg `@latest` tarball, and a fresh clone with submodules uninitialized falls straight through to npm — the submodules are an editing convenience, never a runtime dependency. acptoapi has no refresh script (thebird never imports it directly, see the stack-contract rule above); its submodule exists purely so it can be edited and pushed from inside this checkout.
- **Vendor refresh pipelines** — `recall thebird vendor refresh pipelines`: refresh-design/refresh-freddie/refresh-gm -> docs/vendor/; --local dev boxes / --npm CI; sync-upstream.mjs orchestrates; the three refresh-*.mjs-driven subtrees (gm, kits/os, freddie) each stamp a .version JSON; other vendor/ subtrees are currently unstamped, tracked in `docs/vendor.lock.json`.
