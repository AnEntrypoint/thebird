# thebird

A bash terminal that runs in the browser. Node serves the static files and nothing else.

## Runtime surface

- Node only: `bin/thebird-relay.js`, `src/relay.js`.
- Browser (page and worker): `web/terminal.html`, `web/terminal.js`, `web/pty-adapter.js`, `web/shell-client.js`, `web/shell-worker.js`, `web/bash-shell.js`, `web/builtins.js`, `web/shell-core.js`, `web/shell-sed.js`, `web/shell-tar.js`, `web/shell-jq.js`, `web/shell-awk.js`, `web/shell-program.js`, `web/shell-in-txiki.js`, `web/shell-lookup.js`, `web/git-in-page.js`, `web/git-program.js`, `web/commit-gate.js`, `web/sqlite-in-txiki.js`, `web/sqlite-program.js`, `web/python-in-page.js`, `web/python-worker.js`, `web/python-bundle.js`, `web/splash.js`, `web/curl-in-page.js`, `web/qjs-in-txiki.js`, `web/qjs-program.js`, `web/node-in-txiki.js`, `web/txiki-in-page.js`, `web/fx-in-page.js`, `web/gm-in-page.js`, `web/stream-hub.js`, `web/shims/*.js`.
- Vendored: `web/vendor/acorn.mjs`, `web/vendor/isomorphic-git.mjs`, `web/vendor/brotli/`, `web/vendor/tte-js/`, `web/vendor/fx/` and `web/vendor/gm/` (committed, generated), and the generated `web/vendor/bashkit/`, `web/vendor/txiki/` and `web/vendor/gm/skills/`.
- Scripts: `scripts/browser-driver.mjs`, `scripts/build-pages.mjs`, `scripts/lint-architecture.mjs`, `scripts/lint-comments.mjs`, `scripts/lint-live.mjs` (the architecture lint's live probes, run in their own process), `scripts/vendor-bashkit.mjs`, `scripts/vendor-fx.mjs`, `scripts/vendor-gm.mjs`, `scripts/vendor-txiki.mjs` (compile gate for the txiki core; its browser libuv and libwebsockets placeholder headers are in `scripts/txiki/include/`), `scripts/witness.mjs`, `scripts/witness-shell.mjs` (Node-side groups for `web/shell-core.js`, run by `npm run witness:shell`).

## Browser and Node split

- Everything under `web/` is browser-only. It imports nothing from Node. `web/shims/` modules import only each other.
- `src/relay.js` and `bin/` are Node-only.
- Add a shim in `web/shims/` before adding a `node:` import to in-page code.
- The relay answers GET and HEAD only, binds `127.0.0.1` by default, and must keep sending `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`.

## Comments

- Repo-owned code has no comments. `npm run lint:comments` lists each one with its file and line, and exits non-zero when there are any.
- When a change touches a file, remove the comments in that file as part of the change. Prose that cannot become self-explanatory code moves to `AGENTS.md` or `ARCHITECTURE.md`, after checking it is still true.
- Shebang lines in `bin/` are syntax, not comments.
- Vendored bundles keep their upstream comments and are not edited. `lint:comments` reports them as VENDORED and fails a vendored file with comments that has no provenance entry in `scripts/lint-comments.mjs` and is not listed in `web/vendor/fx/manifest.json`.

- `web/vendor/acorn.mjs` and `web/vendor/isomorphic-git.mjs` are committed unmodified. Do not edit them.
- `web/vendor/xterm/` is xterm.js, committed unmodified. It is the terminal in the page, loaded as plain ES modules and a stylesheet with no build step. Versions, from the npm tarballs: `@xterm/xterm` 6.0.0 (`xterm.mjs`, `xterm.css`), `@xterm/addon-fit` 0.11.0 (`addon-fit.mjs`), `@xterm/addon-webgl` 0.19.0 (`addon-webgl.mjs`). The page loads it and sets `term.unicode.activeVersion = "11"`, which needs `allowProposedApi`. Do not edit them; a new version is a new vendor step with the new hashes.
- `web/vendor/bashkit/` is generated by `scripts/vendor-bashkit.mjs`, gitignored, and checked against pinned SHA-256 values. Run the script after a fresh clone; it needs network.
- `web/vendor/fx/` is the libfx SDK modules and the fx core WASM (`fx-core.wasm`), committed as generated by `scripts/vendor-fx.mjs` from the sibling fx checkout or `FX_REPO`. `manifest.json` records each file's SHA-256. Its JavaScript modules keep upstream comments, and `scripts/lint-comments.mjs` accepts each one because `manifest.json` lists it. Pages rebuilds them from gmfx `main` on each deploy.
- `web/vendor/gm/` is generated by `scripts/vendor-gm.mjs` from the sibling gm checkout or `GM_REPO`. `gm-core.wasm` is a Zig `wasm32-wasi` build of gm's portable C++ `json.cpp`, `sha256.cpp` and `compact.cpp` with `scripts/gm/bridge.cpp` as its C ABI. `gm-core.js` instantiates it through `web/shims/wasi-preview1.js`. `skills.js` embeds gm's three served skills. `web/gm-in-page.js` is gm's stdio MCP server: each `rpc` line is one JSON-RPC message, the three served tools are `next_context`, `run_code` and `finish`, and every other verb is `gm.<name>` inside a `run_code` body. The log resumes the newest run under `/workspace/.gm/runs`. Pages rebuilds it from gm `main` on each deploy.
- Pyodide is not vendored or generated: the page fetches the stripped bundle at run time, and the witness reads the Pyodide 314.0.7 lock from its pinned jsDelivr URL (`https://cdn.jsdelivr.net/pyodide/v314.0.7/full/pyodide-lock.json`) and checks its SHA-256 before it reads micropip from it.
- Python runs from the stripped bundle `https://anentrypoint.github.io/pyodide-minimal/pyodide-minimal.br` (format pyodide-minimal, version 1), fetched at run time and never committed. `web/python-bundle.js` decodes it with the vendored brotli decoder, checks each file's SHA-256 against the manifest and the Pyodide 314.0.7 core against pins, and hands the files to `web/python-worker.js`. The tte-js `laseretch` splash (`web/splash.js`) covers the load and falls back to plain text.
- pip loads micropip from the CDN at run time, pinned to the Pyodide version, and fetches pure wheels from PyPI. Packages in the bundle's lock are refused. Do not add wheels to `web/vendor/` without owner approval.

## Browser state

- History is kept in localStorage under `thebird.history`. It stores only the submitted command lines, capped at 500. No output, cwd or other state.
- Output is drawn by xterm.js (vendored, see Vendored). It renders colour, bold, cursor movement, clear screen and the alternate screen. `web/pty-adapter.js` keeps the input line and passes keys and paste in. Wide characters: xterm draws CJK and emoji two cells wide (Unicode 11 via the vendored addon). The adapter places the input cursor with a width table for the East Asian wide and emoji ranges and the zero-width ranges in `web/pty-adapter.js`; a character outside those ranges counts one cell. On each resize the page sends the terminal size, and the shell sets the COLUMNS and LINES shell variables before the next command.
- `which`, `command -v` and `type` are defined in `web/shell-lookup.js` and must agree for every in-page builtin. The builtins are `git`, `sqlite3`, `python3`, `pip`, `qjs`, `tjs`, `node`, `curl`, `wget`, `fx` and `gm`.
- `node` is an alias for txiki. `node <script>`, `node -e <code>` and `node -v` run through `web/node-in-txiki.js` on the same engine as `tjs -e`, so the page has no separate JavaScript runtime. Scripts get txiki's globals and module loader, not Node's `require`, `process` or `Buffer`.

## Timeout

`COMMAND_TIMEOUT_MS` in `web/bash-shell.js` is 900000 and is passed to bashkit's `Bash` as `timeoutMs`. Do not lower it: the first cold `python3` or `pip` call takes 210 s run alone and 546 s to 600 s or more under contention, as recorded in `ARCHITECTURE.md`. bashkit's `execute()` ignores a per-call `timeoutMs`, so the limit is shared by every command line. Change the value only with a witnessed cold install.

## Cancel

- Ctrl-C ends a `curl` or `wget` waiting on the network. The fetch is aborted, the command exits 130 with `cancelled`, and the page leaves the busy state.
- `python3` and `pip` run in a dedicated worker, `web/python-worker.js`, which holds Pyodide. Ctrl-C terminates that worker, so a busy script stops and a `pip` download in progress is abandoned. The command exits 130 with `cancelled`, and the next `python3` or `pip` starts a new worker. This needs no shared memory and no cross-origin isolation.
- A cancel loses Python's in-memory state: globals, imported modules, files outside `/workspace`, and packages installed by earlier `pip` runs, which live in the worker's memory. Files a cancelled script wrote to `/workspace` are not kept, because the workspace takes Python's writes only when a run finishes. The first `python3` after a cancel is slower, because Pyodide starts again.
- `git` has no network await: `web/git-in-page.js` refuses `clone`, `fetch`, `pull` and `push` before the txiki engine starts, so no request is made and there is nothing to abort.
- A `node`, `tjs`, `qjs`, `git`, `sqlite3`, `curl` or `wget` loop that never yields (`node -e "while (true) {}"`) is stopped by Ctrl-C through the engine's interrupt handler on a cross-origin isolated page, which the local relay is. The command exits 130 with `cancelled` and the directory survives. On a page that is not isolated, which is the Pages site, the shell worker cannot read the cancel while the loop runs, so the client replaces the worker after 1.5 s: the command reports `cancelled` with 130, and the shell restarts at `/workspace`. The shell's variables are lost in that case.

## Hosting

- `.github/workflows/pages.yml` builds `_site/` with `scripts/build-pages.mjs` on each push to `main` and deploys it to GitHub Pages. Its build job checks out the latest `main` of gmfx and gm owned by AnEntrypoint, builds `fx-core.wasm` and the libfx SDK into `web/vendor/fx/`, builds `gm-core.wasm` into `web/vendor/gm/`, and verifies the generated manifests before the page build. The page needs no cross-origin isolation headers, and the witness runs the built site without them.
- The build job has `contents: read` only. The deploy job alone has `pages: write` and `id-token: write`. The witness checks both blocks.
- The actions in `pages.yml` are pinned to full commit SHAs: actions/checkout `11d5960a326750d5838078e36cf38b85af677262` (v4), used for thebird, gmfx and gm, actions/setup-node `49933ea5288caeca8642d1e84afbd3f7d6820020` (v4), actions/upload-pages-artifact `56afc609e74202658d3ffba0e8f6dda462b719fa` (v3), actions/deploy-pages `d6db90164ac5ed86f2b6aed7e0febac5b3c0c03e` (v4). Each SHA was resolved with `git ls-remote` and confirmed as a commit by `gh api repos/<repo>/git/ref/tags/<tag>`.
- Pinning matters because the deploy job holds `pages: write` and `id-token: write`, and a moved tag would change the code that runs with them. To upgrade, resolve the new SHA the same way, change the `uses:` line, and update this list.
- Do not add a root-absolute path such as `/web/...` to browser code. The Pages site sits under `/thebird/`, so every URL in `web/` is relative to the file that holds it.

## Commit gate

`web/commit-gate.js` is the in-page gate for `git commit`. It checks the index, staging, syntax (acorn), ASCII, the four docs and their repo paths, and a git object round trip. It is not a semantic review. Keep its checks and its `NOT_COVERED` list in step with the code, and with `ARCHITECTURE.md`.

## qjs on the txiki engine

- `qjs -e <code>` runs in the txiki engine, whose quickjs-ng core is compiled into `web/vendor/txiki/tjs.wasm` (`QUICKJS_SOURCES` in `scripts/vendor-txiki.mjs`). `web/qjs-in-txiki.js` passes the code as `args` to the static program `web/qjs-program.js`, which evaluates it with indirect `eval`, prints the value of the last expression unless it is `undefined`, and reports an uncaught exception through the engine.
- The standalone quickjs-ng wasm, its zig build, its pin, its scripts and its witness were retired together with the old page-side runner: no `qjs.wasm` is built or shipped. `web/shims/wasi-preview1.js` stays, because `web/txiki-in-page.js` uses it.

## txiki.js

- `scripts/vendor-txiki.mjs` builds txiki.js v26.11.0 for wasm32-wasi with zig 0.17.1 into `web/vendor/txiki/tjs.wasm`. The gate passes only when every listed file compiles and the link leaves zero undefined symbols. Its libuv is `scripts/txiki/browser/uv-browser.c`, and `scripts/txiki/stubs.tsv` lists every stub and excluded module, one row each.
- The wasm pin is `cc37307b9130d2d2fcfb98ca833527d4e2d29028c67b393f27634e938bacd1b7`, in `TXIKI_WASM_SHA256` and in `.github/workflows/pages.yml`. A local build and a CI build from a different checkout path gave the same bytes.
- The build is reproducible only with the fixed inputs the script sets: `-ffile-prefix-map` for the repo, the staging directory and zig's lib dir, and `ZIG_GLOBAL_CACHE_DIR` at `$TMPDIR/thebird-zig-global-cache`. Zig writes its global cache path into the wasm, so a different cache location changes the hash.
- `tjs -e "<code>"` runs through `web/txiki-in-page.js` and `scripts/txiki/browser/entry.c`. The entry does not call `TJS_Run`, because that runs the file-based `run-main` bootstrap, which reads `tjs.exePath` and fails in the page. It calls `JS_Eval` in module mode on the context, reports a rejected module promise as `Uncaught ...`, then runs turns. Each turn drains pending jobs, runs `uv_run` once in non-blocking mode, and returns: 2 while timers are pending, 0 when none are, 130 when cancelled. The page ticks a waiting engine with `tjs_browser_tick` after a 5 ms pause, so the page event loop runs between turns. A page abort calls `tjs_browser_cancel`; the next turn stops the timers and returns 130, which `node` and `tjs -e` report as `cancelled`. On an isolated page a Ctrl-C also sets the shared cancel word, which the engine's interrupt handler reads through `tjs_cancel_requested`, so a loop with no await stops inside the job. A deadline set per run (`tjs_browser_set_deadline`) stops the job at `timeoutMs` with 124, reported as a timeout. Each run takes an engine instance from a pool, so a builtin nested in another run keeps its own state. Errors go to stderr through the WASI shim.
- sqlite is in the same wasm: the sqlite3 amalgamation from the txiki.js source tree with SQLITE_OS_OTHER=1, txiki's mod_sqlite3 registered as `tjs:sqlite` when the build passes -DTJS_HAVE_SQLITE, and `scripts/txiki/browser/sqlite-vfs.c` as the `thebird` VFS. The VFS calls the `tjs_fs_*` host imports, which `web/txiki-in-page.js` implements over `web/shims/fs.js`, so pages live in the OPFS tree and never on the host. The VFS has no-op locks and omits WAL. Temp files go to `/.thebird/`.
- txiki's `fetch` runs in the page. `scripts/txiki/browser/http-client.js` implements the native `HttpClient` that the fetch polyfill uses, and `httpclient-browser.c` installs it as `core.HttpClient`. The host makes each request with the browser's `fetch`, and the runtime stays alive until the requests end (`tjs_browser_resume`, `tjs_browser_end`). `curl` and `wget` generate a module that calls `fetch`. Do not restore the native `httpclient.c`: it needs libwebsockets.
- `.github/workflows/txiki.yml` runs the gate on pushes that touch the txiki files and on dispatch. `pages.yml` builds the same wasm, checks it against the pin, and ships it with the site.
- Module loading decision (git): the engine's loader refuses `tjs:internal/*` imports from a user module (`modules.c`, the importer must be a `tjs:` module), and it has no host hook for module source. So the git program is carried in the code string. `web/git-in-page.js` concatenates `web/git-program.js`, the text of `web/vendor/isomorphic-git.mjs` and `web/vendor/acorn.mjs` (each wrapped in a function, its trailing `export {...}` rewritten to a return object), and the text of `web/commit-gate.js` (its `import` and `export` keywords removed). The vendored bundles are read as text and not edited.
- The fs binding for git is a native object, `__thebirdFs` (`scripts/txiki/browser/fs-browser.c`). `entry.c` installs it on each new runtime, and the git program deletes the global before anything else runs. It calls the `tjs_fs_*` host imports; `tjs_fs_stat`, `tjs_fs_readdir`, `tjs_fs_mkdir` and `tjs_fs_rmdir` were added to `web/txiki-in-page.js` for it.
- Shell on txiki, assessed and not built: bashkit (`web/vendor/bashkit/`) stays the shell. A txiki shell must supply what bashkit does now: a bash-subset parser (quoting, `$?`, `$(...)`, `;`, `&&`, `||`, pipes, `>`, `>>`, `<`, `2>`), variables and arithmetic, globbing, functions, the `which`, `command -v` and `type` lookups of `web/shell-lookup.js`, the Ctrl-C path through the run's `AbortController`, the `COMMAND_TIMEOUT_MS` expiry, and the `$?` carry. The engine supplies the event loop, the fs binding and `fetch`, but it has no shell parser. That parser is a separate piece of work, and nothing in `scripts/witness.mjs` yet runs against it, so the blocker is the missing parser and its witness.

## Fresh-tree notes

- A tree from `git archive` has no `.git`. The lints call git, so they cannot run there.
- The architecture lint's live checks need `web/vendor/bashkit/` present. The lint does not generate it.
- The `cc242f5` record (the owner commit) is handled as follows. It PASSes when `cc242f5` resolves to a commit object. It is UNVERIFIED (no history) only when the object does not resolve and the tree has one commit. It FAILs when the object does not resolve on a tree with more history.

## Working rules

- Use Conventional Commits.
- Open, flaky: once, a witness run stalled for about 16 minutes after the streamed-output checks, in the terminal block that stores submitted lines. `send` in `scripts/browser-driver.mjs` had no timeout, and `waitFor` checks its deadline only between `evaluate` calls. The stall is not reproduced: the re-run finished with `WITNESS-EXIT 0`. `send` is now bounded at 60 s through `withTimeout`, and the witness checks that a call which never answers aborts.
- `THEBIRD_WITNESS_FIXTURE=desynced-mapping npm run witness` feeds a desynced mapping to the drift check in memory, with gh unavailable. The run must exit 1 with the local FAIL line. Without the variable the run exits 0. No file on disk changes.
- On a slow link the bashkit wasm (7.8 MB) can take minutes to load. The live check passed in 238738 ms with a 1200 s limit, so use a long timeout for live checks on such a network.
- Validation: `npm run check`, `npm run lint:comments`, `npm run lint:architecture`, and `npm run witness`. The witness drives headless Chromium through `scripts/browser-driver.mjs`; set `CHROME_BIN`. There is no test suite.
